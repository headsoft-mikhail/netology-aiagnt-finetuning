# Fine-tuning Qwen2.5-0.5B-Instruct с LoRA

Локальная instruct-модель адаптируется для коротких русскоязычных ответов службы
поддержки интернет-магазина. Pipeline выполняет проверку данных, baseline,
LoRA-обучение, сохраняет checkpoint и adapter, повторно загружает adapter и
сравнивает ответы на неизменном eval-наборе.

## Итог эксперимента

| Метрика | Baseline | Tuned |
| --- | ---: | ---: |
| Eval loss | 1,7137 | 1,4528 |
| Perplexity | 5,5495 | 4,2752 |
| Ответы, прошедшие все критерии | 0 из 5 | 0 из 5 |
| Pass rate | 0% | 0% |

Обучение снизило eval loss на `0,2609` и perplexity на `1,2743`, но ручная
оценка не подтвердила улучшение прикладного качества. Для всех пяти запросов
получен статус `unchanged_fail`; улучшений и регрессий по бинарному критерию нет.
Этот результат подробно объяснён в разделе «Почему качество ответов не выросло».

## Модель и метод

Используется
[Qwen/Qwen2.5-0.5B-Instruct](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct),
revision `7ae557604adf67be50417f59c2c2f167def9a775`. Это causal instruct-модель
примерно на 0,49 млрд параметров с русским языком и chat template.

Выбрана LoRA, потому что модель помещается в 16 GiB unified memory в float32 и
обучается через MPS без 4-bit backend. QLoRA для такого запуска не требуется.
Основные веса заморожены; обучаются adapter-слои `q_proj` и `v_proj`:

- `r: 8`;
- `lora_alpha: 16`;
- `lora_dropout: 0.05`;
- `bias: none`;
- 540 672 обучаемых параметра из 494 573 440, или 0,1093%.

Ограничения базовой модели: небольшой размер, ошибки в фактах и слабое следование
инструкции. Поэтому улучшение качества после короткого обучения не гарантируется.

## Окружение

Проверенный запуск выполнен на macOS arm64 с 16 GiB unified memory:

- Python 3.12.14;
- PyTorch 2.14.0;
- Transformers 5.17.0;
- PEFT 0.21.0;
- устройство MPS;
- dtype float32;
- CPU доступен как запасной вариант; CUDA и XPU недоступны.

Зависимости перечислены без ограничений версий в `pyproject.toml`. Команда
`just lock` выбирает последние совместимые версии, а `uv.lock` фиксирует
фактически использованное окружение.

## Установка

Все команды выполняются из корня репозитория:

```bash
just setup
just python 3.12.14
just lock
just install
just lint
```

`just python` пересоздаёт `.venv`, поэтому повторно запускать эту команду нужно
только при первоначальной настройке или смене Python. Для установки уже
зафиксированных зависимостей достаточно `just install`.

Публичная модель скачивается один раз без Hugging Face token:

```bash
just download_model
```

Ожидаемый локальный каталог:
`data/models/base/Qwen2.5-0.5B-Instruct/`. Базовые веса исключены из Git.
`.env.example` не нужен, потому что pipeline не использует токены или другие
секреты.

## Данные

Файлы `data/fine_tuning/train.jsonl` и `data/fine_tuning/eval.jsonl` используют
единый формат: уникальный строковый `id` и сообщения в порядке
`system → user → assistant`.

- Train: 32 примера поддержки интернет-магазина.
- Eval: 5 отдельно написанных запросов с новыми формулировками.
- Длины с chat template: 62–99 токенов для train и 71–99 для eval.
- Максимальная длина: 512 токенов.

Валидация проверяет корректность JSONL, обязательные поля, роли, пустые значения,
уникальность ID и диалогов, пересечения train/eval, единый system prompt,
максимальную длину, признаки секретов, телефоны и адреса электронной почты.
Критическая ошибка останавливает запуск до обучения. Проверены отдельные отказы
при битом JSON, повторном ID, пересечении train/eval и пустом ответе assistant.

```bash
just validate_data
just validate_config
```

Номер `8-800-000-00-00` разрешён как фиктивный заполнитель из учебного набора.
Настоящих секретов и персональных данных в датасетах нет.

## Конфигурация

Все пути и ключевые параметры находятся в `config/fine_tuning.yaml`: модель,
revision, seed, устройство, dtype, максимальная длина, LoRA, Trainer, сохранение
и генерация. Основные параметры запуска:

- seed `42`;
- learning rate `0.0002`;
- batch size `1` для train и eval;
- gradient accumulation `4`;
- две эпохи;
- линейный scheduler с warmup `0.03`;
- evaluation и сохранение после каждой эпохи;
- `save_total_limit: 1`;
- детерминированная генерация: `do_sample=false`, `max_new_tokens=128`.

## Запуск

Перед обучением можно отдельно проверить оборудование и локальную модель:

```bash
just inspect_env
just inspect_env cpu
just inspect_env gpu
```

Полный воспроизводимый цикл после скачивания базовой модели:

```bash
just fine_tune
```

Команда последовательно проверяет окружение и конфигурацию, выполняет baseline,
обучение, сохранение checkpoint и adapter, повторную загрузку adapter, tuned
evaluation и сравнение.

Этапы также можно запустить отдельно:

```bash
just train
just evaluate
```

`just train` включает baseline и обучение. `just evaluate` загружает чистую
базовую модель и итоговый adapter, затем создаёт tuned-отчёт и comparison-отчёт.
Загрузка выполняется с `local_files_only=true`: строка `Loading weights` означает
чтение локальных весов с диска, а не повторное скачивание модели.

## Токенизация и обучение

`AssistantResponseDataset` применяет chat template отдельно к prompt и полному
диалогу. Токены system/user и padding получают label `-100`; в loss остаётся
только ответ assistant. Для всех 37 примеров проверено, что длины `input_ids` и
`labels` совпадают, prompt замаскирован, а 23–53 assistant-токена участвуют в
loss.

Trainer выполнил 16 шагов за две эпохи на MPS примерно за 27 секунд. Средний
training loss равен `1,3421`. Loss по отдельным шагам менялся шумно: от `1,4896`
на первом шаге до `0,9308` на последнем, с промежуточным максимумом `1,9241`.
Eval loss снизился с `1,5220` после первой эпохи до `1,4528` после второй.

Сохранены:

- `data/fine_tuning/runs/support_lora_minimal/checkpoint-16/` — checkpoint
  Trainer с adapter, optimizer, scheduler, RNG и состоянием обучения, около
  17 МБ;
- `data/models/adapters/support_lora_minimal/` — итоговый adapter и tokenizer,
  около 13 МБ.

Оба каталога включены в репозиторий. Полные базовые веса модели в Git не входят.

## Оценка и отчёты

Baseline и tuned проверяются на одинаковых eval-примерах, с одинаковыми system
prompt, параметрами генерации и критериями:

1. русский язык;
2. краткость и ответ по существу;
3. соответствие правилам из эталона;
4. отсутствие выдуманных условий.

Пример проходит проверку, только если выполнены все четыре критерия. Ручные
оценки и обоснования хранятся в `data/fine_tuning/manual_evaluation.json`.

Итоговые файлы:

- `data/fine_tuning/reports/baseline_report.json`;
- `data/fine_tuning/reports/training_report.json`;
- `data/fine_tuning/reports/tuned_report.json`;
- `data/fine_tuning/reports/comparison_report.json`.

Comparison report содержит конфигурацию, окружение, log history, время обучения,
loss, perplexity, pass rate, ответы обеих версий, статусы изменений и пути к
артефактам.

## Почему качество ответов не выросло

Наиболее вероятны несколько связанных причин:

1. **Мало семантически разнообразных данных.** В train 32 строки, но многие из
   них являются близкими перефразировками. По ключевым темам eval — возврат,
   статус заказа, повреждение, график поддержки и покупка без аккаунта — есть
   примерно по три очень похожих train-примера. Формального количества достаточно,
   но эффективное разнообразие ниже.
2. **Очень короткое обучение.** Выполнено только 16 шагов оптимизации за две
   эпохи, а LoRA меняла 0,1093% параметров и только модули `q_proj`/`v_proj`.
   Этого хватило для снижения teacher-forced loss, но не для устойчивого изменения
   свободной генерации на новых формулировках.
3. **Ограничения модели 0.5B.** Уже baseline плохо следовал простому system prompt,
   придумывал правила магазина и иногда отказывался отвечать. Небольшой adapter на
   маленьком наборе не исправил эти базовые ограничения.
4. **Loss и прикладной критерий измеряют разное.** Cross-entropy снизилась, то есть
   модель стала лучше предсказывать эталонные токены при teacher forcing. При
   генерации ответ оценивался строгим правилом «все критерии выполнены». Например,
   на `eval_003` tuned-модель перестала отказываться, но придумала отправку письма
   вместо фото в чат поддержки, поэтому пример всё равно не прошёл проверку.
5. **Eval слишком мал для тонких изменений.** Пять примеров и бинарная оценка не
   отражают частичное улучшение отдельных формулировок. Они позволяют честно
   зафиксировать результат этого запуска, но не дают устойчивой оценки качества.

Явных признаков переобучения в двух эпохах нет: eval loss продолжал снижаться.
Однако из-за маленького eval этот вывод ограничен. В следующей итерации следует:

- добавить разнообразные примеры именно по пяти проваленным темам;
- расширить eval и добавить более детальные критерии вместо одной бинарной оценки;
- проверить больше эпох с выбором лучшего checkpoint по eval loss;
- сравнить текущие `q_proj`/`v_proj` с `q_proj`/`k_proj`/`v_proj`/`o_proj`;
- при сохранении слабых ответов перейти на более сильную модель 1–1.5B.

Отсутствие роста pass rate не считается ошибкой pipeline: обучение завершилось,
adapter повторно загрузился, метрики и ответы объективно сопоставлены. Результат
зафиксирован без утверждения, что модель стала лучше, поскольку это не
подтверждено ручной оценкой.
