# План минимального решения «Практика fine-tuning»

Дата: 16 сентября 2026 года. Репозиторий: `netology-aiagnt-finetuning`.
Рабочая ветка: `fine-tuning`, созданная от локальной `main`.

[Условие задания](https://netology.ru/profile/program/aiagnt-1/lessons/651858/lesson_items/3501310).
На странице указан срок сдачи: 23 сентября, 23:59.

План выполняется по шагам. На шаге 1 готовим окружение; обучение и сравнение качества относятся к следующим шагам.

## 1. Объём решения

Сделать воспроизводимый локальный цикл одной командой:

`проверки → baseline → LoRA-обучение → checkpoint и adapter → повторная загрузка adapter → tuned evaluation → сравнение и JSON-отчёты`.

Использовать одну causal instruct-модель и только LoRA. Обойтись без QLoRA, MLflow, отдельного smoke-конфига, resume, веб-интерфейса, интеграции с агентом, перебора моделей и самостоятельного CLI для каждого этапа.

В условии есть неоднозначности: masking, perplexity, log history и ограничение checkpoints встречаются и в основном описании, и среди расширений. Выполним эти небольшие проверки и вычисления, чтобы покрыть подробные требования. Отдельный manifest и автоматическую экспертную оценку не делаем: для минимального уровня достаточно метаданных в итоговом отчёте и зафиксированной ручной оценки.

## 2. Выбранный подход

- **Задача:** краткие русскоязычные ответы поддержки учебного интернет-магазина, соответствующие предоставленным правилам и без выдуманных условий.
- **Модель:** `Qwen/Qwen2.5-0.5B-Instruct` — небольшая causal instruct-модель примерно на 0.49B параметров с поддержкой русского языка и chat template. [Карточка модели](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct).
- **Метод:** обычная LoRA с замороженными базовыми весами; не нужен backend для 4-bit-квантования.
- **Окружение:** отдельная `.venv`, Python 3.12.14 через `just python`; PyTorch, Transformers, PEFT, Accelerate, PyYAML. JSONL читаем стандартным `json`, данные подаём через простой PyTorch Dataset; TRL и Datasets не обязательны.
- **Устройство:** macOS arm64 с 16 GiB unified memory. PyTorch видит MPS; модель и короткая генерация проверены на MPS в float32. Запасной вариант — CPU с float32. Конкретные device/dtype фиксируем в YAML, без универсального менеджера всех ускорителей.
- **Модель скачать заранее** в `data/models/base/Qwen2.5-0.5B-Instruct`, зафиксировать revision модели; библиотеки перечислить без ограничений версий в `pyproject.toml`, последние совместимые версии выбрать через `just lock` и сохранить в `uv.lock`. Обучение и inference работают с локальным каталогом. Веса базовой модели исключить из Git.

- [x] Указать команду скачивания модели и ожидаемый локальный путь в README. Публичная модель скачивается без HF token; `.env.example` и ключ Groq не нужны.

### Шаг 2. Подготовить train и eval

- [x] Взять 33 диалога из `../netology-dataset-fine-tuning/train_dataset.jsonl` как исходный материал для train. После просмотра удалить один смысловой дефект: вопрос о покрытии гарантии имел ответ только о её сроке. Сохранить 32 примера с уникальными строковыми `id`.
- [x] Написать отдельно 5 eval-примеров по той же задаче и правилам магазина с новыми формулировками. Не переносить в eval готовые перефразировки из train.
- [x] Зафиксировать eval до обучения и не менять его ради улучшения результата. Темы совпадают с train, но формулировки запросов новые.
- [x] В каждом примере оставить `id` и `messages` в порядке `system → user → assistant`. Использовать единый system prompt. Дополнительные поля keywords/tags не использовать.
- [x] Проверить JSON, непустые сообщения, допустимые роли, наличие user и финального assistant, уникальность ID, отсутствие пересечений ID, запросов и диалогов, дубликатов, секретов и персональных контактов. Фиктивный номер-заполнитель из исходного набора явно разрешить.
- [x] Проверять длину полного диалога локальным tokenizer и chat template Qwen. Получено 62–99 токенов для train и 71–99 для eval при лимите 512; слишком длинный пример отклоняется с указанием ID.

### Шаг 3. Сделать YAML-конфигурацию

Все пути, параметры модели, обучения, LoRA и генерации читаются из `config/fine_tuning.yaml`.

- [x] Сохранить в YAML идентификатор запуска и seed, все входные и выходные пути,
  идентификатор и revision модели, device/dtype, параметры LoRA, Trainer и генерации.
- [x] Реализовать `FineTuningConfigManager`, который загружает YAML, проверяет типы,
  диапазоны, допустимые значения, связи между секциями и существование входных путей.
- [x] Добавить `just validate_config`: команда проверяет конфигурацию, затем использует
  пути и `max_seq_length` из неё для полной проверки train/eval.

Зафиксированные значения первого учебного запуска:

| Параметр | Значение |
| --- | --- |
| seed | 42 |
| method | lora |
| r / lora_alpha / lora_dropout | 8 / 16 / 0.05 |
| bias | none |
| target_modules | q_proj, v_proj; проверить наличие в загруженной модели |
| learning_rate | 0.0002 |
| train/eval batch size | 1 / 1 |
| gradient_accumulation_steps | 4 |
| num_train_epochs | 2 |
| max_seq_length | 512 |
| logging_steps | 1 |
| eval_strategy / save_strategy | epoch / epoch |
| save_total_limit | 1 |
| generation | do_sample=false, max_new_tokens=128 |

Сохранение по эпохам гарантирует checkpoint даже на маленьком датасете. Прежде чем оценивать результаты, проверить, что шаги оптимизации действительно выполняются. Параметры можно скорректировать из-за памяти или ошибок запуска, но итоговый конфиг и фактические значения должны совпадать.

### Шаг 4. Реализовать baseline, токенизацию и обучение

- [ ] До изменения весов получить baseline-ответы на всех eval-примерах и baseline eval_loss. При генерации передавать только system/user, без эталонного assistant.
- [ ] Сохранить `baseline_report.json`: ID, system prompt, запрос, эталон, фактический ответ, параметры генерации, критерии оценки.
- [ ] Использовать chat template модели, подготовить input_ids, attention_mask и labels. Маскировать prompt и padding значением `-100`; убедиться, что assistant-токены остаются в loss и длины тензоров совпадают. Проверить корректность границы prompt/answer для выбранного шаблона.
- [ ] Подключить LoRA, вывести число обучаемых параметров и убедиться, что базовые веса заморожены.
- [ ] Запустить Transformers Trainer. Писать в консоль и log history train_loss, eval_loss, epoch/step, learning rate; измерить время обучения.
- [ ] Сохранить минимум один настоящий Trainer checkpoint, финальный adapter и tokenizer. Adapter сохранять отдельно от полной базовой модели.

### Шаг 5. Повторно загрузить adapter и сравнить результаты

- [ ] Освободить обучавшуюся модель, заново загрузить ту же базовую модель и сохранённый adapter с диска. Провести tuned evaluation на неизменном eval с теми же prompts и настройками генерации.
- [ ] Сохранить `tuned_report.json`, eval_loss и perplexity (`exp(eval_loss)` с обработкой переполнения).
- [ ] Вручную оценить обе версии по заранее заданным одинаковым критериям: русский язык, краткость, ответ по существу, соответствие эталонным правилам, отсутствие выдуманных условий. Для каждого ответа сохранить `passed` и краткое обоснование. До ручной оценки значение должно быть `null`, а не вымышленным результатом.
- [ ] Сформировать `comparison_report.json`: оба ответа, оценки и один из статусов `improved`, `regressed`, `unchanged_pass`, `unchanged_fail` для каждого ID. Добавить baseline/tuned pass rate и количества изменений.
- [ ] В итоговый comparison report включить конфиг/модель/revision, seed, окружение, число примеров, log history, время, loss, perplexity и пути к артефактам. Это заменяет отдельный manifest в минимальном решении.
- [ ] Описать фактические улучшения, регрессии и ограничения. Рост качества не гарантирован и не является условием завершения эксперимента; отсутствие улучшения честно отразить в выводе.

### Шаг 6. Проверить воспроизводимость и оформить сдачу

- [ ] Проверить отказ до обучения при испорченном JSON, повторном ID, пересечении train/eval и пустом ответе; отдельно проверить masking на одном реальном токенизированном примере.
- [ ] Выполнить полный учебный запуск; убедиться, что checkpoint, adapter и отчёты существуют, JSON читается, все eval ID сопоставлены, adapter действительно повторно загружается.

Для крупных артефактов указать расположение, размер и способ получения; одного локального пути, недоступного проверяющему, недостаточно. Базовые веса в Git не добавлять.

Общую оркестрацию и небольшую функцию сравнения разместить в существующих модулях. Предполагаемая команда:

```bash
python -m fine_tuning.train --config config/fine_tuning.yaml
```

Ручную оценку сохранить в JSON-отчётах; пересчёт сравнения сделать небольшой вызываемой функцией, не повторяя обучение и не создавая отдельную систему команд.

## 5. Критерий завершения

Работа готова, когда выполнен полный цикл на настоящей модели, сохранены train/eval loss, хотя бы один checkpoint и итоговый adapter, adapter повторно загружен, получены и оценены ответы до/после на одинаковом eval, сформированы три отчёта и инструкция воспроизведения. Небольшой размер eval и возможное переобучение отражены в выводах. Публикация и отправка решения — отдельный следующий шаг после реализации.
